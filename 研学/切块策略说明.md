# 切块策略说明

本文说明本项目中**文本如何切分**，以及**参数与实现为什么这么选**，便于答辩与后续调参。

---

## 一、当前切块逻辑（两阶段）

实现位置：`src/chunking.py`。

### 1. 按「第X回」拆成章节

- 用正则匹配形如「第…回…」的标题行（到换行），将全书拆成多组 `(章节序号, 标题, 正文)`。
- `chapter_no` 按标题**出现顺序**从 1 递增编号，不从标题里解析「第一百二十回」等数字，避免繁体/异体解析复杂度。
- 若全书未匹配到任何「第X回」，将全文兜底为「第1回 未识别标题」，避免整本书被丢弃。

### 2. 章内滑动窗口细切

- 对每一章的 `body` 再切分：**每块最多 800 字符**，**相邻块重叠 160 字符**。
- 空串会跳过；`chunk_size` 必须大于 `overlap`，否则直接报错。

### 3. 生成 `chunk_id` 与 `summary`

- `chunk_id`：`ch{章序号三位}_{块序号三位}`，例如第 1 回第 3 块 → `ch001_003`。
- `summary`（教学版）：取该块内**到第一个句号「。」为止**作为首句，超过 80 字则截断并加 `...`；若无句号则用正文前缀。

---

## 二、为什么这么选

### 1. 先按「回」再细切

- **《三国演义》天然按回组织**：回目是强语义边界，比纯按字数切更符合书体与读者预期。
- **检索与引用更清晰**：每块可挂 `chapter_title`，答辩和 Attu 里都能一眼对应到「哪一回」。
- **避免单回过长**：一整回直接向量化，信息密度过高，检索时容易「糊」；必须在回内再切细。

### 2. 窗口 800、重叠 160

- **800 字量级**：对中文叙事常能包住一小段情节或几句对话，语义相对完整；同时块数可控，入库与检索成本可接受。
- **重叠 160**：减少「关键句正好落在两块边界」被切断的概率，**召回更稳**；重叠越大块数越多、成本越高，160 是常见折中。
- **可调**：没有唯一标准答案，生产环境通常用实验（Recall@k、人工看 bad case）微调 `chunk_size` 与 `overlap`。

### 3. 摘要用规则而非 LLM

- **零外部依赖、可复现**：课堂与答辩环境稳定，不因模型或额度波动。
- **角色明确**：`summary` 主要用于列表与预览；答题与证据仍以 `content` 为主。生产可替换为 LLM 摘要以提升语义质量。

### 4. 章节序号用顺序号

- **实现简单、边界少**：不解析「一百二十」等写法，减少 bug 面。
- **对 RAG 足够**：溯源主要依赖 `chapter_title` + `content`；顺序号便于排序与生成稳定 `chunk_id`。

## 三、与代码的对应关系

| 能力           | 函数              | 要点                         |
|----------------|-------------------|------------------------------|
| 章切分         | `split_by_chapter`| 正则 + split 配对标题与正文  |
| 滑窗           | `sliding_chunks`  | 800 / 160                    |
| 摘要           | `make_summary`    | 首句 + 80 字截断             |
| 总入口         | `build_chunks`    | 遍历章 → 滑窗 → Chunk 列表 |

---

## 四、后续可扩展方向（答辩可提）

- 按段落、对话、引号等二次边界再切，减少语义碎片。
- 章内先粗切再按 token/字符预算对齐 embedding 上限。
- 用 LLM 做语义切块（成本高、需评测与稳定性方案）。
- 超参数走小评测集调优，而不是拍脑袋定死。
