# RAG 理解升级版（课上版）

## 1. RAG 的核心定义

RAG（Retrieval-Augmented Generation）不是“让大模型直接回答”，而是：

1. 先从知识库检索相关证据；
2. 再把证据喂给大模型生成答案；
3. 同时返回引用来源，保证可追溯、可解释。

---

## 2. 标准工程链路（8步）

### 第一步：数据准备

- 收集文档并做清洗（去噪、去重、统一编码）。
- 明确文档结构（章节、段落、标题层级）。

### 第二步：切块（Chunking）

- 先按业务结构切（例如《三国演义》按“第X回”）。
- 再做滑动窗口细切（例如 chunk_size=800, overlap=160）。
- 每块生成稳定 `chunk_id`，并保留章节元数据。

### 第三步：向量化（Embedding）

- 使用同一 embedding 模型对“文档块”和“查询问题”向量化。
- 向量维度要与向量库 schema 一致（例如 768）。

### 第四步：向量库建模与入库

- 设计 schema：`id / chapter_no / chapter_title / summary / content / vector`。
- 建立向量索引（如 HNSW + COSINE）。
- 完成批量入库与基础校验（行数、索引状态）。

### 第五步：检索（Retrieval）

- 将用户问题向量化后进行 top_k 检索。
- 可升级为混合召回（向量 + BM25）提升召回完整性。

### 第六步：重排（Rerank，可选）

- 对召回候选做相关性重排，降低“看似相关但不精确”的噪声。
- 输出更高质量上下文给生成模型。

### 第七步：生成（Generation）

- 将问题 + 检索上下文拼接为提示词交给 LLM。
- 输出答案时附带 citations（块 id、章节、片段）。

### 第八步：服务化与交付

- 提供 API（如 FastAPI 的 `/ask`、`/health`）。
- 结合前端页面与管理工具（如 Attu）做可视化验证。

---

## 3. 评测与迭代（决定系统是否“真的好用”）

建议至少有三类指标：

1. **召回指标**：Recall@k（正确证据是否被召回）  
2. **答案指标**：回答正确率 / 一致性  
3. **引用指标**：引用命中率（答案是否真的基于已检索证据）

优化顺序建议：

1. 先调切块；
2. 再换/调 embedding；
3. 再加混合召回；
4. 最后加 reranker 精排。

---

## 4. 与普通“AI 问答”最大的区别

- 普通问答：模型可能“凭记忆/幻觉”回答。
- RAG 问答：答案基于检索证据，有来源可查。

一句话总结：  
**RAG 的价值不只是“能答”，而是“答得有依据”。**

---

## 5. 本项目对应（答辩可直接说）

- 切块：按回目 + 滑窗；
- 存储：Milvus 集合 `sanguo_chunks`；
- 检索：向量 top_k；
- 生成：LLM 或教学回退；
- 输出：`answer + citations`。

这已经形成了“可运行、可验证、可扩展”的最小 RAG 闭环。
